# 要件定義（レビュー用ドラフト）

**状態**: ユーザーレビュー待ち  
**対象**: 体重・運動管理Webアプリ  
**要件質問票**: `aidlc-docs/inception/requirements/requirement-verification-questions.md`

## Intent Analysis

- **依頼種別**: Greenfieldの新規アプリケーション
- **目的**: 体重、日々の運動・ミッション、食事画像を記録し、カレンダーで継続状況を確認する
- **利用者**: 主利用者は1名。主に1台で利用するが、AWS上のJSONデータを複数端末で同期する
- **アプリ形態**: スマートフォン対応Webアプリ。PWA対応を含む
- **規模・複雑度**: 中〜高。個人の健康情報と画像を扱い、AWS同期、同時更新、URLを知る人への未認証アクセスを含む

## Functional Requirements

### FR-01 カレンダー

- 月単位のカレンダーを表示する。
- 当日は他の日と区別できる枠線で示す。
- 各日には記録内容と達成状態を反映する。

### FR-02 体重記録

- kg単位で日付ごとに1件の体重を記録できる。
- 過去日の記録を追加・修正できる。
- 体重を記録すると、その日の体重項目を完了として扱う。

### FR-03 運動ノルマとデイリーミッション

- 運動ノルマと標準ミッションを日ごとに表示し、個別に達成状態を記録できる。
- 標準ミッションを追加・編集できる。
- 初回アクセス時に1〜15件の標準ミッションを設定し、設定後は日次ミッションが0件にならないようにする。
- ミッション編集は将来日に適用し、過去日の内容と達成状態は保持する。初回設定前の日付への適用は確認中。
- 具体的な初期ミッション名・目標値は設計時に決める。質問票では指定されていない。

### FR-04 月間目標

- ユーザーが月間目標を入力・編集できる。
- 対象月のカレンダー上部に目標を常時表示する。

### FR-05 日ごとのミッション表示

- カレンダーの日付を選ぶと、その日のミッション一覧をモーダル表示する。

### FR-06 食事画像

- カメラロール等の端末内画像をWebアプリに取り込める。
- 1日につき最大2枚の料理画像を日付に添付・表示できる。
- JPEG、PNG、WebPを受け付け、1枚あたり10 MBまでとする。
- 添付済み画像を個別削除できる。削除前に確認し、月次JSONの参照とS3オブジェクトを整合させる。
- 画像の添付は日次完了条件に含めない。
- カメラロールからWebアプリへ画像をインポートできる。アプリ内撮影は不要で、カメラロールへの自動保存も行わない。

### FR-07 日次完了表示

- 体重記録、運動ノルマ、全デイリーミッションが完了した日を完了色で表示する。
- 食事画像の有無は完了判定に影響させない。

### FR-08 保存・同期

- リレーショナルデータベースは使用せず、構造化データをJSONとしてAWS上に保存する。
- 画面で表示・編集するアプリデータの通常の保存先をS3上のJSONとし、表示時はそのJSONを読み込む。
- 複数端末間で同じデータを同期する。
- 同時更新時にデータが意図せず上書き・欠落しないようにする。
- 古い月次JSONバージョンからの更新は拒否し、最新データを示して再読込・再適用を案内する。後着更新で自動上書きしない。
- S3バケットは非公開とし、データアクセスはアプリ経由に限定する。画像本体はS3オブジェクト、JSONには画像参照情報を保持する方式を設計候補とする。

### FR-09 アクセス方式

- ログイン認証は設けない。
- アプリのURLを知る人は、アプリを利用してデータを閲覧できる。
- S3自体を公開せず、アプリ経由でデータにアクセスさせる。
- 個別の閲覧者・編集者ロールは要件にないため、アクセス者間の権限分離は行わない前提でレビューする。

### FR-10 バックアップ・復元・全データ削除

- アプリ内のバックアップ／復元機能は提供しない。通常データはFR-08のS3 JSONへ保存する。
- アプリからの全データ一括削除機能は提供しない。日付に添付した個別画像の削除はFR-06に従う。

## Non-Functional Requirements

### NFR-01 対応端末

スマートフォンでの利用を優先したレスポンシブWeb UIとし、PWA対応を含める。オフライン利用は指定されていない。

### NFR-02 データ保護とアクセス上の注意

- 体重と画像は機微な個人情報として扱う。
- Q16・Q17の回答により、URLを知る人はログインなしで利用可能とする。この方式は非公開・本人限定アクセスではなく、URLが第三者に知られた場合にデータを閲覧されるリスクがある。
- HTTPS通信とS3の非公開設定を前提とする。未認証アクセスを選択したため、URLを認証手段や秘密情報として扱える保証はない。
- AWSリソースを作成・公開する前に、アカウント、リージョン、アクセス方式、想定費用を明示し、ユーザーの承認を得る。

### NFR-03 データ整合性

複数端末・複数のURL利用者による同時更新を考慮する。月次JSONの読込バージョンが古い更新は拒否し、最新値を表示して利用者に再読込・再適用を促す。後着更新で先行更新を黙って上書きしない。

### NFR-04 配色

次の14色のみを使用し、指定外の色は追加しない。背景・文字・状態表示の組み合わせは可読性を考慮して選ぶ。

`#e30f25`, `#0c7bbb`, `#f8c112`, `#7f1184`, `#eafdff`, `#f68b1f`, `#7cfc00`, `#00afcc`, `#f6adc6`, `#ea533a`, `#7a99cf`, `#f6ae54`, `#7b68ee`, `#f0f8ff`

### NFR-05 テスト

プロパティベーステストは部分適用とする。純粋関数とJSONの保存・復元往復を対象にし、PBT-02、PBT-03、PBT-07、PBT-08、PBT-09を適用する。通常の例ベーステストも併用する。

### NFR-06 拡張設定

- Security Baseline: 無効
- Property-Based Testing: 部分適用
- Resiliency Baseline: 無効

### NFR-07 AWS配置

- 希望リージョン: 東京（`ap-northeast-1`）
- 独自ドメイン: 不要
- 月額費用上限、AWSアカウント、実際のデプロイ承認: 未確定。構成・見積もりを提示し、別途承認を得るまでデプロイしない。

## レビュー時の重要確認事項

1. URLを知る人がログインなしで健康情報と画像を閲覧できる方式を、ユーザーは選択している。これは本人限定の非公開アプリとは異なるため、公開前にこのリスクとアクセス方式を再確認する。
2. S3上のJSONはアプリの通常の永続化先であり、手動インポート／エクスポートとは別の要件である。同時更新時の競合解決方式、初期ミッション内容は設計段階で具体化する。
3. アプリ内バックアップ／復元と全データ一括削除は行わない。画像は個別削除できる。
4. 初回ミッション設定より前の日付に対するミッション適用と、独立した運動ノルマの具体的な内容はFunctional Designで確認中。
5. AWSの利用料金とアカウント・デプロイ条件は、実リソース作成前に別途承認を得る。
